# ADR-001: Native clients and a portable, engine-isolated domain

- **Status:** Proposed baseline. The portable scoring primitive is host-built and tested; native clients, FFI bindings and VPN engines are not implemented or build-verified.
- **Date:** 2026-11-14.
- **Decision owners:** V2Speed product/engineering (human approval still required for engine/license choice).

## Context

V2Speed needs a real mobile VPN, different OS tunnel APIs, high-performance protocol engines, and shared policy/Smart Connect behavior. The repository starts empty. The reference app is Android-only and GPL-3.0. Its current Android wrapper builds Xray; there is no iOS implementation in the reference. iOS Network Extension entitlements and a real Apple build/signing path are not available in this environment.

## Options considered

| Option | Performance / compatibility | Native lifecycle & UX | Maintainability / testability | Security / feasibility |
|---|---|---|---|---|
| A. Native Android Kotlin + native iOS Swift, shared Go core | Best potential protocol engine reuse and native UX; a Go core can be efficient, but exact mobile support and protocol versions must be pinned | First-class `VpnService` and `NetworkExtension`; native UI | Separate platform adapters/UI; Go shared core requires two mobile bindings and platform-specific protection | Existing Android binding is not proof of iOS feasibility; Go/core license and static distribution need legal review; platform tunnel API constraints remain native |
| B. KMP shared models/policy + native UIs/adapters | Strong domain reuse; packet handling should remain in engine/native layer | Native `VpnService`/`NetworkExtension`, Compose/SwiftUI | Shared Kotlin logic and golden-vector tests reduce duplicated scoring; KMP/Xcode integration adds build complexity | Good boundary if KMP stays above packet I/O; iOS interoperability/toolchain must be proven |
| C. Flutter/React Native with native tunnel plugins | UI iteration can be fast; no benefit to data-plane performance; plugins/cores still platform-specific | Requires native bridge/plugins for both VPN lifecycles and platform APIs | One UI codebase but bridge/plugin lifecycle coupling; possible split-brain state | Third-party plugin trust/maintenance risk; does not solve core licensing, entitlements or protocol parity |

## Decision

**Use native user interfaces and native VPN lifecycle adapters. Keep the domain/core boundary independent from the UI and platform tunnel APIs.** Android UI/service will use Kotlin and iOS UI/provider Swift. The small deterministic Smart Connect scorer, state reducer and fallback planner are implemented as a portable C ABI so both native clients can use identical tested domain decisions; they perform no network, tunnel or packet processing. Platform probing, real connection orchestration, configuration validation and OS-state reconciliation stay behind native adapters and must be verified separately. Do not put packet processing in KMP or the UI runtime.

**Do not adopt a cross-platform VPN-engine binding until a technical and legal spike validates a pinned core on Android and iOS.** Xray-core is a candidate for an independently written adapter, not selected/approved for release. Native or alternative cores remain an option if the feature, license, packaging and performance matrices show a material advantage.

## Consequences

- Native UI, lifecycle, permissions, secure storage and VPN APIs can be correctly represented and tested.
- The scoring primitive is a single C implementation; probe orchestration, state transitions, platform integrations and measurement collection still differ and require explicit cross-platform contract tests.
- Android/iOS engine protocol support may initially differ. Feature availability must be explicitly capability-gated, not faked.
- iOS support is blocked on a real Xcode build, Network Extension entitlement, supported core binding, and device verification.
- The decision must be revisited after a time-boxed spike with measurements and legal clearance; no commercial release should rely on this provisional selection.

## Alternatives rejected for now

- Flutter/React Native is not selected solely to share UI because core/VPN lifecycle still requires native integration and adds a bridge boundary.
- KMP for low-level packet I/O is rejected; KMP may later be used for domain logic only if Xcode integration is proven to be lower risk than golden-vector parity.
- A mandatory backend is rejected: local profiles and tunnels should work without account/server API infrastructure.
